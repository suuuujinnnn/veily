# 업체찾기 라벨 체계 v3 설계

2026-08-15 작성. UI/UX 개편에 맞춰 업체찾기의 라벨 분류를 처음부터 다시 잡고, 베리굿웨딩 제휴 업체 40곳의 인스타그램 사진을 수집·라벨링한다.

## 왜 다시 하는가

`feature/vendor-search-instagram` 브랜치에서 만든 `taxonomy.json` v2는 그 시점의 화면을 기준으로 축을 잡았다. 그 사이 develop의 업체찾기 UI가 바뀌면서 라벨 분류가 다른 물건이 됐다.

| | develop (지금 UI) | taxonomy.json v2 |
|---|---|---|
| 분야 | 드레스 / 헤어 / 메이크업 / 스튜디오 / 웨딩홀 | 드레스 / 헤어&메이크업 / 스튜디오 / 웨딩홀 |
| 드레스 | 소재1 · 소재2레이스 · 소재3비즈 · 상체라인 · 스커트라인 · 특별디자인 · 촬영2부 | 넥라인 · 소재 · 라인 · 트레인 · 장식 · 색상 · 오버레이 |
| 헤어 | 공간프라이버시 · 담당자진행 · 시간동선 · 추가서비스 · 다운 · 업스타일 | 묶음위치 · 묶음형태 · 마감 · 길이 · 텍스처 · 장식 · 브레이드 |
| 스튜디오 | 화면구성 · 무드 22개 · 빛컬러 · 공간장면 · 시간구도 · 소품 | 인원 · 배경씬 · 컷구성 · 시간대 · 색감 · 무드 6개 · 소품 |
| 웨딩홀 | 키워드 그룹 0개 (별도 `VenueFilterPanel`) | 공간종류 · 연회형 · 좌석배치 · 밝기 · 주광원 |

축 이름만 다른 게 아니라 분야 수도, 한 축에 들어가는 개념도 다르다. v2 라벨을 그대로 새 UI에 꽂으면 상당수가 걸릴 자리가 없다.

여기에 더해, 그대로 두면 검색이 망가지는 지점이 넷 더 있다.

**헤어 축 넷이 사진에서 판정 불가능하다.** `단독룸`·`원장 지정 가능`·`얼리 스타트 가능`·`커트 가능` 같은 값은 이미지에 존재하지 않는 정보다. 모델에게 물으면 그럴듯한 값을 지어낸다.

**스튜디오 무드가 22개다.** v2 검증에서 감성·로맨틱·사랑스러움·러블리가 표본 18장 전부에 참이라 변별력이 0으로 측정됐고, 그래서 6개로 줄였던 목록이다. 새 UI에 22개가 그대로 돌아와 있다.

**드레스 `상체 라인` 한 축에 넥라인과 소매가 섞여 있다.** 오프숄더에 긴팔소매인 드레스는 두 값이 동시에 참인데 축이 하나라 하나가 버려진다.

**`촬영·2부` 그룹의 값이 전부 색상이다.** 그룹 이름은 용도인데 담긴 값은 색상이라 본식 드레스에 색상을 붙일 자리가 애매하다.

## 제약

작업 전에 확정한 것들이다.

- **프론트 UI 무수정.** `.tsx`와 `.css`는 한 줄도 건드리지 않는다.
- **라벨 값 유지.** 축 구조는 고치되 UI에 노출된 키워드 문자열은 지우거나 바꾸지 않는다.
- **이미지 인식은 Claude Code 세션에서 직접 수행한다.** `ANTHROPIC_API_KEY` 과금 경로를 쓰지 않으므로 `server/src/classify` 계열은 이번 범위에 없다.
- **업체 4종 × 10곳.** 드레스 10 · 스튜디오 10 · 헤어메이크업 10 · 웨딩홀 10. 헤어메이크업샵 10곳이 UI의 헤어와 메이크업 두 분야를 함께 채운다.
- **업체당 인식 상한 없음.** 받아온 사진은 전부 라벨링한다.
- **웨딩홀은 메타데이터만.** 사진 라벨은 달지 않는다.

## 3층 데이터 모델

UI를 안 건드리면서 이미지로 판정 불가능한 축을 분리한다 — 언뜻 모순처럼 들리지만 실제로는 아니다. `WeddingReference.tags`가 평평한 `string[]`이고, UI가 태그의 출처를 묻지 않기 때문이다. `weddingReferenceData.ts`의 헤어 태그에는 이미 `단독룸`(운영조건)과 `로우 번`(디자인)이 한 배열에 섞여 들어가 있다.

그래서 출처 구분을 데이터 레이어에서 끝낸다.

```
L0 원자 라벨 (data/labels.jsonl)
   사진 한 장에서 실제로 판정 가능한 것만. 세션에서 직접 인식.
        │
        │  L1 매핑 규칙 (src/data/labelMapping.ts)
        ▼
L1 UI 키워드 (WeddingReference.tags: string[])
   referenceKeywordData의 키워드와 1:1. 화면이 읽는 유일한 층.
        ▲
        │
L2 업체 메타데이터 (src/data/vendorFacts.ts)
   단독룸·원장지정·얼리스타트·지역·홀타입. 인식 대상이 아니다.
```

L0과 L2가 각각 규칙을 거쳐 같은 `tags` 배열로 합류한다. 컴포넌트 입장에서는 지금과 똑같은 데이터가 들어온다.

이 구조의 값어치는 다음 개편 때 나온다. UI가 또 갈아엎어져도 `labelMapping.ts`만 고치면 되고, 사진 1,000장을 다시 인식하는 일이 생기지 않는다. 이번에 라벨링을 처음부터 다시 하게 된 이유가 정확히 그 다시 인식하는 일이었다.

## referenceKeywordData 구조 변경

세 군데를 고친다. 키워드 문자열은 하나도 지우지 않는다.

**드레스 `상체 라인` 12개를 둘로 나눈다.**

```
이전  상체 라인: 일자탑 하트탑 상체디테일탑 오프숄더 스퀘어넥 하트스퀘어넥
                브이넥 홀터넥 하이넥 라운드넥 반팔소매 긴팔소매
이후  넥라인:   일자탑 하트탑 상체디테일탑 오프숄더 스퀘어넥 하트스퀘어넥
                브이넥 홀터넥 하이넥 라운드넥
      소매:     반팔소매 긴팔소매
```

같은 축의 값은 OR, 다른 축끼리는 AND로 묶이므로 나누면 "오프숄더면서 긴팔"이 검색된다. 지금은 둘 중 하나만 남는다.

**드레스 `촬영·2부`를 `색상`으로 바꾼다.** 값은 그대로다. `화이트`가 이미 목록에 있어서 본식 드레스도 이 축에 들어간다.

**스튜디오 무드 22개는 목록을 유지한다.** 대신 L0에서 지배적인 값 1~2개만 배타적으로 부여한다. 사진마다 해당되는 무드를 전부 붙이면 v2에서 측정된 변별력 0이 재현된다. 키워드는 살리고 부여 규칙으로 푼다.

`ReferenceSearchPanel`은 `currentCategory.groups`를 순회 렌더링하므로 데이터 파일만 바꿔도 화면이 따라온다. 컴포넌트 수정은 없다.

## 카테고리별 L0 축

L0은 사진에서 판정 가능한 것만 담는다. L1으로 가는 매핑을 함께 적는다.

### 드레스

| L0 축 | 성격 | L1 대상 그룹 |
|---|---|---|
| 넥라인 | 배타 1값 | 넥라인 |
| 소매 | 배타 1값 (없으면 미부여) | 소매 |
| 소재 | 다중 | 소재1, 소재2·레이스 |
| 장식 | 다중 | 소재3·비즈 |
| 스커트라인 | 배타 1값 | 스커트 라인 |
| 특별디자인 | 다중 | 특별 디자인 |
| 색상 | 배타 1값 | 색상 |
| 프레이밍 | 게이팅 전용 | 없음 |
| 오버레이 | 보정 전용 | 없음 |

프레이밍(클로즈업·반신·전신)은 화면에 안 나가지만 게이팅에 쓴다. 오버레이(케이프·볼레로)도 화면에 안 나가는데, v2 검증에서 케이프를 드레스 본체로 읽으면 스트랩리스가 하이넥+긴팔로 뒤집히는 사고가 확인됐다. 넥라인 판정을 지키려면 오버레이를 따로 인지해야 한다.

### 헤어

| L0 축 | L1 대상 그룹 |
|---|---|
| 묶음위치 (로우/미들/하이) | 디자인·업스타일 |
| 묶음형태 (번/포니/땋음) | 디자인·업스타일 |
| 길이 (단발/장발) | 디자인·다운 |
| 텍스처 (생머리/웨이브) | 디자인·다운 |
| 반묶음 여부 | 디자인·다운 |

`로우 번` 같은 L1 키워드는 L0의 묶음위치와 묶음형태를 조합해서 만든다. 둘 중 하나라도 판정이 안 되면 키워드를 부여하지 않는다.

헤어의 나머지 네 그룹(공간·프라이버시, 담당자·진행, 시간·동선, 추가 서비스)은 L2다. L0 인식 대상이 아니다.

### 메이크업

| L0 축 | L1 대상 그룹 |
|---|---|
| 피부표현 | 피부 표현 |
| 무드컬러 | 무드·컬러 |

축 구조가 이미 1:1이라 손댈 게 없다. 다만 v2에서 촬영 조건 편향이 확인된 축이다. 에이바이봄 표본 10장이 전부 하이키 조명이라 어떤 베이스든 광이 떠서 피부 축이 물광 하나로 붕괴했다. 피부 라벨은 조명 조건을 함께 기록한다.

### 스튜디오

| L0 축 | 성격 | L1 대상 그룹 |
|---|---|---|
| 화면구성 | 배타 1값 | 화면 구성 |
| 무드 | 지배 1~2값 | 무드·분위기 |
| 빛컬러 | 다중 | 빛·컬러 |
| 공간장면 | 다중 | 공간·장면 |
| 시간구도 | 다중 | 시간·구도 |
| 소품 | 다중 | 소품 |

### 웨딩홀

L0 없음. `weddingVenueData.ts`의 메타데이터만 채운다. 지역·접근 지점·식사·홀타입·희망조건은 전부 베리굿웨딩 홀 검색에서 가져온다.

## 게이팅과 abstain

v2 검증의 결론 하나를 그대로 가져온다. **모든 사진에 모든 축을 시도하면 안 된다.**

```
① 사진 종류 게이팅   제품컷 / 부대시설 / 브랜드그래픽 / 텍스트카드
                    제품컷이 아니면 라벨도 파일도 남기지 않는다
② 샷 타입 분류      클로즈업 / 반신 / 전신 / 공간
③ 포즈·각도         기립 여부, 정면·측면·후면
④ 축별 시도 결정    판정 불가면 abstain
```

근거가 된 사례들이다.

- 얼굴 클로즈업은 메이크업에 최적이지만 헤어 정보는 0에 가깝다. 게이팅 없이는 클로즈업에 헤어 라벨을 억지로 붙이는 오류가 대량 발생한다.
- 좌식·기댄 포즈는 실루엣 축을 통째로 무효화한다. 기립 여부를 먼저 보고 스커트라인은 시도조차 하지 않는다.
- 생머리는 부재의 증명이라 정면 컷으로는 원리적으로 확인 불가능하다. 뒤에서 묶었는지 알 수 없다.
- 흑백 사진에 색상 축을 붙이면 거짓말이 된다.

abstain은 실패가 아니다. 판정 불가는 `labels.jsonl`에서 그냥 키가 빠지고, 검색에서 제외된다. v2에서 드레스 라인 커버리지가 50%였던 건 라벨 문제가 아니라 인스타 화보에 밑단이 안 보이는 컷이 많아서였다.

값을 유지하기로 했으므로 근접 촬영 없이 구분이 안 되는 값들(`미카도 실크`와 `오간자 실크`, `블망 레이스`와 `캐미컬 레이스`)도 목록에 남는다. 이런 값은 확신이 없으면 상위 개념만 붙이거나 abstain 한다. 억지로 고르지 않는다.

## 수집 파이프라인

```
베리굿웨딩 제휴 목록 → 인스타 계정 매핑 → business_discovery
   → 이미지 게시물 10개 → 캐러셀 children 전개 → public/vendors/ 다운로드
   → 세션에서 인식 → data/labels.jsonl → 생성기 → src/data/weddingReferenceData.ts
```

### 업체 소스

베리굿웨딩(`verygoodwedding.co.kr`)의 제휴 업체 목록을 모집단으로 쓴다. `/gallary/ajax_gallery_list.asp`에 `data=71|72|73`을 POST 하면 목록이 온다.

| 분야 | 코드 | 제휴 업체 수 |
|---|---|---|
| 드레스 | 71 | 125곳 |
| 스튜디오 | 72 | 168곳 |
| 헤어메이크업 | 73 | 90곳 |
| 웨딩홀 | `/hall/hall_search.asp` | 별도 |

기존에 수집된 13개 계정이 이미 이 목록 소속이다. 이룬·아뜰리에오화·에스메랄다·엔조최재훈·꼬모스튜디오·비마이스튜디오·아카이브비·히나프·에이바이봄·정샘물인스피레이션이 전부 제휴 업체다. 버릴 이유가 없으므로 그대로 살리고 10곳까지 채운다.

업체명에서 인스타 계정으로 가는 매핑은 자동화되지 않는다. 후보를 정리해 조회 성공 여부까지 확인한 뒤 목록을 확정한다.

### 게시물 선정 규칙

**"최근 게시물 10개"를 쓰면 안 된다.** 실측에서 에이바이봄의 최근 게시물 10개가 전부 릴스라 사진이 0장 나왔다. 헤어메이크업 계정은 피드가 릴스 위주인 경우가 흔하다.

규칙은 **"이미지가 있는 게시물 10개"**다. `media_type`이 `VIDEO`이거나 `media_product_type`이 `REELS`면 건너뛰고, 10개를 채울 때까지 페이지네이션한다.

캐러셀은 `children`을 전부 전개한다. 장마다 다른 드레스가 걸리는 일이 흔해서 표지 한 장으로 대표시키면 안 된다.

### 실측 편차

| 업체 | 게시물 10개 → 사진 |
|---|---|
| 꼬모스튜디오 | 80장 (10개 전부 캐러셀) |
| 정샘물인스피레이션 | 22장 |
| 이룬 | 20장 |
| 아뜰리에오화 | 10장 |
| 에이바이봄 | 0장 (10개 전부 릴스) |

30곳 합계는 600~1,200장으로 추정된다. 상한 없이 전부 인식하기로 했으므로 한 세션에 끝나지 않는다. **업체 단위로 배치를 끊고 카테고리 순으로 진행한다.** 배치가 중간에 끊겨도 이미 라벨이 있는 사진은 경로로 걸러 건너뛴다.

### 사진 저장

인스타 CDN URL은 서명이 붙어 며칠이면 만료된다. 원격 URL을 라벨에 박아두면 보드가 조용히 깨진다. 반드시 내려받는다.

```
public/vendors/<분야>/<계정>/ig_<미디어ID>[_<children인덱스>].jpg
```

Vite가 `public/`을 루트로 서빙하므로 `reference.image = '/vendors/dressshop/eloon_official/ig_xxx.jpg'`로 그대로 걸린다. 서버 라우트도, 컴포넌트 수정도 필요 없다.

`public/vendors/`는 gitignore 한다. AGENTS.md가 생성 산출물을 저장소에 넣지 말라고 했고, 1,000장을 커밋하면 저장소가 감당이 안 된다. 대신 `data/labels.jsonl`은 텍스트라 커밋하고, 재수집 스크립트로 사진을 복원한다.

## 검증

1. **타입체크와 빌드.** `npm run build`가 통과해야 한다.
2. **UI 무수정 확인.** `git diff --stat`에 `.tsx`·`.css`가 하나도 없어야 한다. 이게 이번 작업의 핵심 제약이라 자동으로 확인할 수 있게 둔다.
3. **키워드 보존 확인.** 개편 전후 `referenceKeywordData`의 키워드 문자열 집합이 같아야 한다. 그룹 이름과 소속만 바뀐다.
4. **매핑 왕복.** `labels.jsonl`의 모든 L0 값이 L1 키워드로 떨어지거나, 의도적으로 안 떨어진다는 게 매핑 표에 적혀 있어야 한다. 갈 곳 없는 L0 값은 인식 낭비다.
5. **변별력 측정.** 축별로 한 값이 표본의 80%를 넘으면 그 축은 검색에 쓸모가 없다. v2에서 스튜디오 무드가 이걸로 걸렸다. 카테고리 한 곳을 끝낼 때마다 잰다.
6. **사람 눈 검수.** 카테고리당 20~30장을 직접 대조한다. v2에서 자동 라벨과 사람 라벨의 일치도를 측정하지 않은 게 한계로 남았다.

## 리스크

**베리굿웨딩 홀 검색 페이지가 응답이 느리다.** `hall_search.asp` 요청이 90초 안에 안 끝났다. 웨딩홀 10곳 메타데이터 수집은 다른 경로가 필요할 수 있다.

**제휴 업체가 전부 비즈니스 계정은 아니다.** `business_discovery`는 개인 계정을 조회하지 못한다. 후보를 넉넉히 잡고 조회 성공한 것만 10곳으로 확정한다.

**워터마크와 저작권 오버레이는 API로도 안 없어진다.** v2에서 에이바이봄 10장 전부, 꼬모스튜디오 4장에서 프레임 하단 15~20%가 판정 불가였다. 해당 영역이 필요한 축은 abstain 한다.

**업체당 10개 게시물은 전수가 아니라 표본이다.** 한 업체의 스타일을 단정하는 근거로 쓰면 안 된다. 인터뷰에서 플래너들이 정확히 이 지점을 경고했다. "이 업체 = 과즙 메이크업"처럼 강하게 분류하면 고객이 절대적 특성으로 인식하는데, 실제로는 담당자 영향이 훨씬 크다는 지적이다.
