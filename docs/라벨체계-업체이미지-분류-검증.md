## 0. 한 줄 요약

**라벨 체계는 사람이 읽는 설명서로는 훌륭하지만, 사진 한 장을 보고 라벨을 붙이는 판정 규칙으로는 아직 쓸 수 없다.**

업체 11곳 148장을 실제로 분류해본 결과, **"그대로 사용 가능"이 나온 업체는 0곳**이었다. 그런데 원인의 대부분이 이미지 품질이 아니라 **라벨 체계 쪽**에 있었다. 이게 좋은 소식이다 — 사진을 다시 모으는 것보다 라벨을 고치는 게 훨씬 싸다.

## 1. 어떻게 검증했나

두 단계로 나눠서 진행했다.

**1단계 — 라벨 기준 보정.** 카테고리별로 가이드 문서를 읽고 **레퍼런스 이미지를 실제로 열어봤다**(총 163장). 파일명만 보고 추측하지 않았다. 그 다음 각 라벨에 대해 "사진 한 장을 보고 이 라벨인지 판정하는 구체적 시각 기준"을 다시 썼고, 판별 난이도를 A/B/C로 매겼다.

| 등급 | 뜻 |
|---|---|
| **A** | 사진만으로 확실히 판정 가능 |
| **B** | 조건부 — 각도·크롭에 따라 갈림 |
| **C** | **사진만으로 판정 불가** (주관적이거나 정보 부족) |

**2단계 — 실전 적용.** 보정된 기준으로 업체 12곳의 이미지를 **한 장도 빠짐없이 실제로 열어서** 라벨을 붙이고, 실패 사례를 수집했다.

> 업체 12곳 중 `chouchoumonde`(웨딩홀) 1곳은 처리 중 오류로 결과를 얻지 못했다. **아래 통계는 11곳 148장 기준**이다.

## 3. 이미지 소스는 문제가 아니었다 (그리고 API가 이걸 없앤다)

### 3-1. `.png`는 인스타 스크린샷, `.jpg`는 원본

148장 중 **36장(24%)이 인스타그램 화면 스크린샷**이고, 전부 `.png` 파일이었다. 찍혀 있는 UI:

- 캐러셀 좌/우 이동 화살표 (반투명 원형 버튼)
- 캐러셀 하단 인디케이터 점 — `choijaehoon`의 경우 **점이 15~20개**인 게시물도 있었다
- 좌하단 프로필 아바타 아이콘
- 피드 4:5 비율 맞춤용 흰 레터박스

실제 피해 사례:

> `ccomostudio/image (4).png` — 좌하단 프로필 아이콘과 캐러셀 점이 드레스 밑단과 바닥에 겹쳐, **'계란후라이' 판정의 핵심 근거인 치마 원형 퍼짐 하단부를 가렸다.**

> `_bemy_studio/image (4).png` — 캐러셀 화살표가 배경씬 판정에 쓰이는 좌측 관목 영역을 가렸다.

### 3-2. 그런데 이건 곧 사라지는 문제다

**Instagram API로 전환하면 스크린샷 24%는 통째로 사라진다.** `media_url`은 UI 없는 원본을 준다. 캐러셀도 `children{media_url}`로 내부 이미지를 개별로 받으므로 인디케이터 점 자체가 없다.

→ **UI 가림 실패(9건)는 API 전환만으로 자동 해결된다.** 지금 이 문제를 고치려고 이미지를 다시 수집하는 데 시간을 쓰지 마라.

### 3-3. 다만 API로도 안 없어지는 오염이 있다

| 오염 | 사례 | API 전환 후 |
|---|---|---|
| 인스타 UI | 캐러셀 점·화살표 | ✅ 사라짐 |
| 흰 레터박스 | archive_boda 8장, ccomo 7장, eloon 다수 | ✅ 대부분 사라짐 |
| **업체 워터마크** | `A BY BOM`(10/10장), `ccomo STUDIO`, `HINAF`, `STUDIO GOYOU`, `ELOON` | ❌ **원본에 박혀 있어 그대로** |
| **저작권 URL 오버레이** | ccomo 4장에 `©2025 monin company...` — **프레임 하단 15~20%가 판정 불가 영역** | ❌ 그대로 |
| **저해상도·강압축** | hinaf 10장 전부 660x840 / 41~80KB | 🔶 API는 더 큰 원본을 주므로 개선 |

> **드레스 라인 축이 3/10.** 판정 기준이 전부 '밑단 폭 대 어깨너비'에 걸려 있는데, 좌식 포즈 2장·상반신 크롭 4장·비정형 밑단 1장에서 밑단이 안 보인다. 인스타 화보가 원래 이런 구성이다.
>
> **헤어 묶음 형태 축이 3/10.** 번/포니 구분, 높이 3분류, 반묶음의 두 층 구조 — **판정선이 전부 뒷모습을 요구하는데 웨딩 화보에 뒷모습 컷이 거의 없다.** abybom은 10장 중 뒷모습이 **0장**이었다.
>
> **'생머리'는 부재(不在)의 증명이라 정면 컷으로는 원리적으로 확인 불가능하다.** 뒤에서 묶었는지 알 수 없다. 이걸 '확실'로 표기하는 라벨러가 있으면 데이터에 계통 오차가 들어간다.

### 4-4. 촬영 조건이 축을 통째로 무너뜨린다

가장 위험한 유형이다. **라벨이 대상을 측정하는 게 아니라 조명을 측정하게 된다.**

> `abybom` — 10장 전부 배경을 날린 하이키 스튜디오 화보라 **어떤 베이스를 썼든 피부에 광이 뜬다.** 결과: 물광 10/10, 세미매트 0, 투명 0, 누디 0. 피부표현 축이 한 값으로 붕괴했다.
>
> **가이드 본문이 스스로 경고한 위험이 실데이터에서 그대로 실현됐다.**
>
> `jsminspiration` — 동일. 물광 9/10. 강한 조명 + 리터칭이 만든 결과라 **축이 메이크업이 아니라 촬영 조건을 측정하고 있을 위험이 있다.**

같은 일이 웨딩홀에서도 일어났다.

> `hotelpj_wedding` — 실내 9/9, 인공조명 9/9. **전 이미지에서 참이라 필터로서 정보량이 0**이다. 반대로 자연광·초록초록·싱그러움·통창·단독홀·스몰은 0/9. **부여율이 100%거나 0%인 라벨이 축의 절반을 넘는다.**

## 6. 가이드 문서 자체의 문제

라벨 이전에 문서에서 발견된 것들이다.

### 6-1. 네 문서 모두 "이게 맞는지 모르겠다"고 적혀 있다

드레스·헤어·메이크업·스튜디오·웨딩홀 가이드의 마지막 절 제목이 전부:

> `# 분류 키워드? (이렇게 하는 게 맞을지 판단 필요)`

**작성자 스스로 미확정 초안임을 표시한 상태로 커밋되어 있다.** 이 검증의 답은 "아니오, 아직 아니다"이고, 아래가 그 근거다.

### 6-2. 판정 기준이 아니라 감상문이다

> 헤어 가이드: "여신 머리의 대표", "얼굴이 작아보인다는 장점", **"디즈니 공주 머리같지 않나요?!"**, "아테네 여신 분위기나고"
>
> 드레스 가이드: **"피팅 시 '와…' 하는 감탄이 절로 나오는 실루엣"**, "하체비만 컴플렉스가 있을 때", "임신 초기 신부"

로우번/미들번/하이번을 가르는 **높이 경계가 문서 어디에도 없다.**

### 6-3. 레퍼런스 이미지와 라벨이 뒤바뀐 사례

이건 그냥 고쳐야 한다.

| 파일 | 문제 |
|---|---|
| `studio/컨페티컷.png` | **컨페티가 없다.** 흩날리는 건 흰 생화 꽃잎이다. 반대로 `인물 중심 1.png`이 전형적인 컨페티 컷(금색·회색 원형 종이) |
| `dress/굵은 비즈 드레스.avif` | **굵은 비즈가 없다.** 확대하면 미세 스팽글로, '맑은 비즈'와 같은 부류. 실제 굵은 비즈는 `비즈 드레스 3/4.jpg`에 있는데 굵기 구분 없는 이름 |
| `makeup/강하게.jpg` | **라벨과 반대 인상.** 창백한 톤다운 베이스에 채도 없는 누드 립. 같은 폴더 `음영 1.webp`(레드 립 + 뚜렷한 아이라인)가 오히려 훨씬 강하다 |

| `weddinghall/채플 컨벤션 웨딩홀 1.png` | 아치 너머 밤하늘·호수가 **실제 창밖이 아니라 벽화·세트.** 유리 프레임 분할선과 반사가 전혀 없다. 그대로 두면 '통창'·'야외' 오라벨 유발 |

### 6-4. 데이터 위생

- **동일 파일 중복**: `studio/야외 스냅.png`와 `studio/야외.png`의 md5가 **완전히 동일**(`c0691a8cc19b3e8f52810aac37aca1be`)
- **콜라주**: 드레스 avif 9개가 **서로 다른 드레스 3벌을 이어붙인 가로 3분할 이미지**다. 파일 단위 라벨이 성립하지 않는다
- **3D 렌더링**: 웨딩홀 레퍼런스 15장 중 **5장(33%)이 실사가 아니라 CG**다. 조명·재질이 실사와 달라 여기서 기준을 뽑으면 실제 사진에 적용되지 않는다
- **비웨딩 이미지**: 헤어 레퍼런스에 하퍼스바자 화보, **칸 레드카펫 포토콜**, 런웨이 백스테이지 컷이 섞여 있다
- **AVIF 디코딩 실패**: makeup 폴더 5장이 표준 이미지 경로에서 열리지 않아 PNG 변환 후에야 확인 가능했다
- **저작권**: 드레스 소재 8장이 외부 블로그 편집 이미지로, **`출처_브라이드메이`, `출처_그레이스듀` 등 워터마크가 남아 있고 라벨 텍스트가 그림 안에 인쇄**되어 있다 (배너 글자가 특징으로 학습될 위험)

## 7. 코드와 문서가 서로 다른 체계를 쓰고 있다

이건 별도로 짚어야 한다. [src/data/vendorStyleData.ts:22-42](src/data/vendorStyleData.ts#L22-L42)의 `vendorStyleTaxonomy`는 레퍼런스 가이드와 **완전히 다른 체계**다.

| | 레퍼런스 가이드 | 코드 (`vendorStyleData.ts`) |
|---|---|---|
| 라벨 총수 | **139개** | **13개** |
| 드레스 | 라인·넥라인·소재·장식·트레인·소매 (32개) | 실크 / **비즈와레이스** / 화려 / **유니크** (4개) |
| 스튜디오 | 7축 61개 | 깔끔함 / 화보 / 초록초록 / 빈티지 / 화려 (5개) |
| 메이크업 | 피부표현·색감 (22개, 헤어 포함) | 과즙 / 깔끔 / 누디 / 강하게 (4개) |
| **웨딩홀** | 24개 | **카테고리 자체가 없음** |

코드의 `비즈와레이스`, `유니크`는 **레퍼런스 가이드에 존재하지 않는 라벨**이다. 반대로 웨딩홀은 가이드에 24개 라벨이 있는데 코드에는 카테고리가 없다.

→ **실서비스 라벨을 확정하기 전에 두 체계를 어느 쪽으로 통일할지 먼저 정해야 한다.** 흥미로운 건, 코드 쪽의 압축된 4~5개 라벨이 이번 검증 결과와 **오히려 방향이 맞다는 점**이다(§8-1 참고).

## 8. 그래서 무엇을 해야 하나

### 8-1. 라벨을 줄여라 — 139개는 너무 많다

이번 검증에서 C등급이 나온 49개는 대부분 **없애거나 합쳐야 한다.**

**즉시 통합·삭제 후보:**

| 조치 | 대상 | 이유 |
|---|---|---|
| 병합 | 투명 + 누디 + 깔끔 + 세미매트 → **'내추럴' 1개** | 5장을 나란히 놓고 구분 불가 |
| 병합 | 벨라인 + 프린세스 → **'벨라인'** | 가이드가 스스로 동일시 |
| 병합 | 터틀넥 + 하이넥 → **'하이넥'** | 시각적 분리 불가 |
| 병합 | 초록초록 + 싱그러움 → **'초록초록'** | 사실상 같은 라벨, 둘 다 예시 0장 |
| 삭제 | 데콜테 | V넥의 부분집합 → V넥의 '깊이' 속성으로 |
| 삭제 | 모던미니멀 | 실루엣이 아니라 소재·장식·무드의 합성 |
| 삭제 | 강하게 | 레퍼런스가 라벨과 반대 인상 |
| **압축** | **스튜디오 무드 22개 → 6~8개** | 확실 판정 0건. 예시 이미지 있는 것만 남길 것 |
| **이관** | 홀타입(일반/컨벤션/호텔), 단독 홀 | **사진이 아니라 업체 메타데이터로** |

> 마지막 항목이 특히 중요하다. `hotelpj`가 실증했듯 **홀타입은 이미지에서 추출 가능한 축이 아니다.** 지금 구조로 학습시키면 모델이 **"어두운 홀 = 호텔"** 같은 업체명 기반 오상관을 학습한다.

### 8-2. 없는 축을 만들어라

**드레스**: 색상(화이트/아이보리/컬러), 오버레이(케이프·볼레로), 일루전 요크, 자수/아플리케
**헤어**: 헤어 액세서리(티아라/핀/생화/리본/베일), 앞머리, 슬릭 vs 루즈 마감, 브레이드 유무
**스튜디오**: **반신컷**(가장 흔한 구도인데 없음), 야외스냅, 골든아워, 역광
**웨딩홀**: 공간 종류(예식홀 / 신부대기실 / 로비 / 연회장 / 외관), 연회형 홀컨셉, 좌석 배치(의자열 vs 라운드 테이블)

### 8-3. 축을 쪼개라 — 한 축에 두 개념이 섞여 있다

| 현재 | 분리 후 |
|---|---|
| 헤어 '묶음 형태' | **위치**(로우/미들/하이) + **형태**(번/포니) + **마감**(슬릭/루즈) |
| 헤어 '푼머리/길이' | **길이**(롱/미디엄/단발) + **텍스처**(생머리/웨이브/컬) ← 묶은 머리에서도 텍스처 정보 유지 |
| 웨딩홀 '조명·분위기' | **밝기**(밝은/중간/어두운) + **주광원**(자연광/인공조명/혼합) |
| 드레스 '라인' | 순수 실루엣만 남기고 장식·무드는 독립 축으로 |
| 시간대 낮/밤 | 낮 / **골든아워** / 밤 |

### 8-4. 파이프라인에 게이팅과 abstain을 넣어라

**이게 가장 중요한 설계 결론이다.** 모든 이미지에 모든 축을 시도하면 안 된다.

```
① 샷 타입 분류        → 얼굴 클로즈업 / 반신 / 전신 / 공간 / 텍스트카드
② 사진 종류 게이팅     → 제품컷 / 로비·부속공간 / 이벤트 공지 / 비제품
③ 포즈·각도 감지       → 기립 여부, 정면/측면/후면 (yaw 추정)
④ 축별 시도 여부 결정
⑤ 판정 불가 시 abstain (억지로 붙이지 않음)
```

근거가 된 실제 실패들:

- **얼굴 클로즈업은 메이크업 축에 최적이지만 헤어 축에는 정보량이 0에 가깝다.** 게이팅 없이는 클로즈업에 헤어 라벨을 억지로 붙이는 오류가 대량 발생한다
- **좌식·기댄 포즈는 실루엣 축을 통째로 무효화한다.** 기립 여부를 먼저 감지해 비기립 컷은 라인·트레인 판정을 시도조차 하지 말아야 한다
- **번/포니 구분은 정면 컷에서 원리적으로 불가능하다.** 강제 분류하면 하이번/하이포니테일 라벨이 무작위로 섞인다
- **메이크업 색감 축은 정면성을 전제로 만들어졌는데 웨딩 화보는 측면·3/4 컷 비중이 매우 높다**
- **통창 검출은 '유리면 검출'이 아니라 '유리 너머 실외 객체 검출'로 구현해야 한다.** 면적만 보는 검출기는 커튼 친 창을 전부 통창으로 오탐한다 (레퍼런스와 벤더 데이터 양쪽에서 재현됨)

### 8-5. 파일명 라벨링을 그만둬라

현재는 폴더가 축, 파일명이 값인 구조인데 **이게 근본적으로 깨져 있다.**

> `dress/반팔 웨딩드레스.jpg` 한 장이 담고 있는 것: 반팔 + 머메이드 + 스탠드칼라 + 무광 크레이프
> → 파일명 하나에 라벨 하나만 붙으니 **나머지 3개 축의 값이 전부 유실된다**

게다가 폴더 규칙도 깨져 있다. `style/` 폴더 13개 중 5개가 넥라인·소매 축 파일이고, 오프숄더는 `style/`과 `neckline/` **양쪽에 중복 존재**한다.

→ **이미지 경로 → 축별 라벨 배열**을 담는 매니페스트(`labels.jsonl`)로 전환하고, 콜라주 avif 9개는 패널 단위로 분할하라.

### 8-6. 라벨당 최소 이미지 기준을 세워라

현재 40%가 예시 이미지 없이 텍스트로만 존재한다.

**제안 기준: 라벨당 정례 2장 + 반례 1장.** 이 기준을 못 채우는 라벨은 확정하지 말고 보류하라. 반례가 중요한 이유는, 이번에 발견된 오류 상당수가 **"이건 A처럼 보이지만 A가 아니다"** 유형이었기 때문이다 (커튼 친 창 ≠ 통창, 벽화 ≠ 야외, 한옥 ≠ 전통혼례).

## 부록 — 검증 방법의 한계

정직하게 남긴다.

- **업체 12곳 중 `chouchoumonde`(웨딩홀) 1곳은 처리 오류로 결과 없음.** 웨딩홀 표본이 2곳 19장으로 가장 얇다
- 업체당 이미지가 7~21장이라 **업체 스타일의 전수가 아니라 표본**이다. `hotelpj`는 9장 중 실질 피사체가 3종뿐이었고 2장은 동일 촬영본 중복이었다
- 판별 난이도 A/B/C와 신뢰도 등급은 **모델 판정이며 사람 라벨러와의 일치도는 측정하지 않았다.** 특히 C등급 판정은 "사람도 못 한다"가 아니라 "사진 한 장 + 현 가이드로는 못 한다"는 뜻이다
- 레퍼런스 이미지는 카테고리별로 39~51장을 실제로 열어 확인했으나, 스튜디오 무드 22개처럼 **예시 이미지가 아예 없는 라벨은 문서 서술만으로 난이도를 매겼다**
