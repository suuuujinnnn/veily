# 업체찾기 작업 인계

2026-08-14 작성. 내 담당 범위는 **업체찾기 페이지**다. 아래 "범위 밖" 항목은 손대지 않는다.

## 지금 어디까지 왔나

인스타그램 Graph API 연동을 끝냈다. 업체 상세의 포트폴리오가 목업이 아니라 실제 게시물을 가져온다.

```
브라우저 → Vite 프록시(/api) → server/ → Graph API → 인스타
```

토큰을 브라우저에 둘 수 없어서 서버를 세웠다. 프론트에서 바뀐 건 인스타 포트폴리오 섹션 한 곳뿐이고, 업체 목록·검색·필터는 아직 목업 그대로다.

### 새로 생긴 파일

```
server/
  src/config.ts                 환경변수 검증 (zod)
  src/instagram/types.ts        Graph 응답 스키마 + 화면 계약 타입
  src/instagram/graphClient.ts  business_discovery 호출, 에러코드 매핑
  src/instagram/mapper.ts       Graph → 화면 계약 변환, 이미지 폴백
  src/routes/instagram.ts       GET /api/vendors/:account/instagram
  src/lib/cache.ts              10분 TTL 캐시

src/lib/instagramApi.ts                       API 클라이언트
src/features/vendors/useInstagramPortfolio.ts 로딩·실패·폴백 상태
```

### 검증 끝난 것

`eloon_official`로 실제 조회에 성공했다. 팔로워 1,638명, 게시물 279건, 캐러셀 내부 이미지까지 전부 들어온다. 없는 계정은 404로 떨어지고, Vite 프록시 경유도 정상이다. 타입체크는 서버·프론트 모두 통과.

`data/vendorStyleData.ts`의 업체 12곳이 전부 실계정이라 토큰만 넣으면 화면에 진짜 포트폴리오가 뜬다.

## 노트북에서 시작하기

### 1. 브랜치

```bash
git fetch origin
git checkout feature/vendor-search-instagram
```

### 2. 의존성

프론트와 서버가 따로다. 둘 다 설치해야 한다.

```bash
npm install
cd server && npm install && cd ..
```

### 3. 토큰 발급 — 이제 한 번만 하면 된다

**`FB_APP_ID` / `FB_APP_SECRET` 을 `server/.env` 에 넣으면 이 단계를 반복할 필요가 없다.** 서버가 토큰을 스스로 끌어올리고 갱신한다.

```
사람이 한 번 로그인 → 단기(1~2h) → fb_exchange_token → 장기(60일)
                                   → /me/accounts → 페이지 토큰(만료 없음)
```

페이지 토큰까지 잡히면 만료가 없어서 재발급 자체가 사라진다. 페이지 토큰을 못 얻는 경우에만 60일 토큰을 **만료 7일 전부터 자동 재교환**한다.

| 경로 | 쓰는 때 |
|---|---|
| `GET /api/auth/instagram/start` | 브라우저로 열면 Facebook 로그인 → 콜백 → 저장까지 자동 |
| `GET /api/auth/instagram/status` | 지금 토큰 종류·남은 일수·권한 확인 (토큰 값은 안 나온다) |
| `POST /api/auth/instagram/token` | Explorer 에서 받은 토큰을 `{"token":"EAA..."}` 로 붙여넣기. 리디렉션 URI 등록 전 우회로 |

`start` 를 쓰려면 Meta 앱의 **유효한 OAuth 리디렉션 URI** 에 `{PUBLIC_BASE_URL}/api/auth/instagram/callback` 을 등록해야 한다. 등록 전이면 세 번째 경로를 쓰면 된다 — 붙여넣은 단기 토큰도 서버가 장기·페이지 토큰으로 바꿔 저장한다.

갱신한 토큰은 `.env` 가 아니라 `server/.secrets/instagram-token.json` 에 0600 으로 쓴다(gitignore 됨). 죽은 토큰은 저장하지 않고 `TOKEN_REJECTED` 로 거절한다.

> ⚠️ **첫 로그인 한 번은 사람이 해야 한다.** OAuth 규격이라 서버가 대신 만들 수 없다. 자동화되는 건 그 이후 전부다.

#### 앱 자격증명 없이 예전 방식으로 받으려면

**토큰은 1~2시간이면 만료된다.** 매번 새로 받아야 하므로 순서를 적어둔다.

[Graph API Explorer](https://developers.facebook.com/tools/explorer)에서:

1. Meta 앱 `veily` 선택, 사용자 토큰 선택
2. 권한 **6개** 확인 — 4개만으로는 안 된다

   ```
   instagram_basic
   instagram_manage_insights
   pages_show_list
   pages_read_engagement
   ads_read              ← 페이지가 비즈니스 포트폴리오 소유라 필요
   business_management   ← 같은 이유
   ```

3. `Generate Access Token` 클릭
4. 팝업에서 포트폴리오 `badger.1681230` 선택 → veily 페이지 체크 → 권한 토글 전부 ON

권한이 4개로만 나오면 [비즈니스 통합](https://www.facebook.com/settings?tab=business_tools)에서 veily 앱을 삭제한 뒤 다시 받는다. 앱에 권한을 추가해도 **기존 토큰에는 실리지 않는다.**

### 4. .env 만들기

`server/.env.example`을 복사해서 `server/.env`로 만들고 토큰만 채운다. gitignore에 걸려 있으니 커밋될 걱정은 없다.

```
IG_ACCESS_TOKEN=EAA...
IG_USER_ID=17841440033789899
```

`IG_USER_ID`는 고정값이라 바꿀 일이 없다.

### 5. 실행 — 터미널 두 개

```bash
cd server && npm run dev     # http://localhost:4000
npm run dev                  # http://localhost:5173
```

동작 확인:

```bash
curl http://localhost:5173/api/health
curl "http://localhost:5173/api/vendors/eloon_official/instagram?limit=3"
```

`{"success":true,...}`에 실제 이미지 URL이 들어 있으면 정상이다.

### 막혔을 때

| 증상 | 원인 |
|---|---|
| `TOKEN_INVALID` | 토큰 만료 + 자동 갱신도 실패. `/api/auth/instagram/start` 로 다시 로그인 |
| `TOKEN_MISSING` | 저장된 토큰이 없음. 위와 동일 |
| `APP_CREDENTIALS_MISSING` | `FB_APP_ID`/`FB_APP_SECRET` 미설정. 자동 갱신이 꺼진 상태 |
| `TOKEN_REJECTED` | 붙여넣은 토큰이 이미 죽었다. Meta 가 준 만료 시각이 응답에 그대로 들어 있다 |
| `me/accounts`가 빈 배열 | 권한 6개 중 `ads_read`·`business_management` 누락 |
| `ACCOUNT_NOT_FOUND` | 대상이 개인 계정이거나 사용자명 오타 |
| 화면에 "데모 데이터" 뱃지 | 서버가 안 떠 있거나 조회 실패. 목업으로 폴백된 상태 |

자세한 배경은 [instagram-api-토큰과-수집범위.md](instagram-api-토큰과-수집범위.md)에 있다.

## 레퍼런스 보드 (2026-08-14 추가)

플래너 요청 그대로다. "미카도 실크 탑 디자인"을 고르면 **여러 드레스샵의 사진이 한 판에 모이고, 사진마다 어느 샵인지 태그가 붙는다.** 인스타를 샵별로 뒤져 캡처하던 과정을 대체하는 화면이다.

업체찾기 안의 세 번째 탭(`레퍼런스로 찾기 / 레퍼런스 보드 / 업체 DB`)으로 들어간다. 기존 `ReferenceSearchPanel` 은 **업체**를 찾고, 이 화면은 **사진**을 찾는다. 결과 단위가 다르니 합치지 않았다.

### 서버

`data/labels.jsonl` 148장을 부팅 때 한 번 읽어 메모리에 두고 검색한다.

```
GET /api/references/search?category=드레스&q=&f=축:값&f=축:값&limit=60&offset=0
GET /api/references/media/<data/vendors 이하 경로>      업체 사진 원본
```

- 조건은 `f=넥라인:스트랩리스` 처럼 반복해서 넘긴다. **같은 축은 OR, 축끼리는 AND.**
- 응답에 결과(`items`)와 함께 조건 목록(`groups`)이 개수까지 담겨 온다. 개수는 "그 축의 선택을 뺀 나머지 조건" 기준이라, 고른 축의 다른 값이 0으로 죽지 않는다.
- 결과는 업체별로 한 장씩 돌아가며 섞는다. 한 샵 사진이 앞을 다 채우면 "여러 샵을 모아 본다"는 목적이 사라진다.

```
server/src/references/paths.ts    data/ 위치 탐색
server/src/references/facets.ts   조건 묶음·롤업·업체 이름표
server/src/references/store.ts    라벨 적재, 검색, 개수 집계
server/src/routes/references.ts   검색 라우트 + 사진 정적 서빙

src/lib/referenceApi.ts                        API 클라이언트
src/features/vendors/useReferenceSearch.ts     조건·요청 상태
src/features/vendors/ReferenceBoard.tsx        보드 화면
src/styles/reference-board.css
```

### 조건 묶음은 taxonomy 축을 그대로 쓰지 않는다

인터뷰 요청 순서(소재 → 장식 → 상체라인 → 스커트라인 → 기타 → 색상)로 다시 묶었다. `facets.ts` 한 곳만 고치면 순서·묶음이 바뀐다.

- **소재 성격 롤업**을 맨 위에 뒀다. `실크 중심 / 레이스 중심 / 비침 소재 / 강한 비즈 / 맑은 비즈 / 장식 없는` — 인터뷰의 "실크 중심인가 비즈 중심인가, 강한 비즈인가 맑은 비즈인가"가 이 여섯 개다. 라벨을 다시 딸 필요 없이 `소재`·`장식` 축을 합쳐 계산한다.
- 과세분화 지적을 받은 `라인`(A라인·벨라인·머메이드·엠파이어·H라인)은 지우지 않고 **접힌 그룹**으로 내렸다. 데이터는 살아 있고 화면 전면에만 없다.

### 토큰 없이도 뜬다

레퍼런스 검색은 인스타를 쓰지 않는데, 예전에는 `IG_ACCESS_TOKEN` 이 없으면 서버가 아예 뜨지 않아 라벨 데이터까지 같이 막혔다. 토큰을 선택값으로 바꿨다. 없으면 부팅 로그에 경고가 뜨고 인스타 포트폴리오만 데모 데이터로 폴백된다(`TOKEN_MISSING`).

### 아직 없는 것

- **커플별 저장** — 담은 시안은 화면 상태로만 있다. 새로고침하면 사라지고 고객 화면으로도 못 넘어간다. 커플 문서에 붙이는 게 다음 단계다.
- **페이지네이션** — 한 번에 60장까지만 내려온다. 지금 데이터가 148장이라 문제가 안 될 뿐이다.
- **업체 이름표** — `facets.ts` 의 `vendorDirectory` 에 계정 12개를 손으로 적어뒀다. 업체 DB 가 서버로 올라오면 지운다.

## 인스타 사진 자동 라벨링 (2026-08-14 추가)

보드에 뜨는 게 수집해 둔 148장뿐이던 문제를 푼다. 인스타에서 사진을 가져와 `taxonomy.json` 기준으로 라벨을 달고 `labels.jsonl` 에 붙이면 곧바로 검색에 걸린다.

```
게시물 조회 → 사진 내려받기 → Claude 비전 분류 → labels.jsonl → 보드 검색
```

```
server/src/classify/taxonomy.ts    taxonomy.json → 구조화 출력 JSON Schema
server/src/classify/classifier.ts  Claude 비전 호출, 응답 검증·정규화
server/src/classify/ingest.ts      조회·다운로드·분류·저장 오케스트레이션
server/src/routes/classify.ts      GET /api/classify/status
                                   POST /api/vendors/:account/classify

src/lib/classifyApi.ts                        API 클라이언트
src/features/vendors/ReferenceSyncPanel.tsx   보드 툴바의 "인스타 동기화"
```

### 사진은 반드시 내려받는다

인스타 CDN URL 은 서명(`oe=`)이 붙어 며칠이면 만료된다. 원격 URL 을 라벨에 박아두면 **보드가 조용히 깨진다.** `data/vendors/<분야>/<계정>/ig_<미디어ID>.jpg` 로 받아 기존 미디어 라우트로 서빙한다.

캐러셀은 장마다 다른 드레스가 걸리는 일이 흔해 내부 이미지를 전부 분류한다. 영상·릴스는 표지 한 장으로 라벨을 달면 틀리기 쉬워 건너뛴다.

### 일반 게시물을 걸러내는 `usable` 게이트

업체 피드에는 드레스 사진만 있는 게 아니다. 아뜰리에 오화 6장을 실제로 받아보니 **2장이 브랜드 명함 카드와 문구만 얹은 꽃 그래픽이었다.** 이런 이미지는 모든 축이 비어도 "라벨 없는 사진"으로 보드에 남아 검색을 더럽히고, 다음 실행 때 또 분류 대상이 되어 중복 과금까지 난다.

응답 스키마 맨 앞에 `usable` 을 두고, false 면 라벨도 파일도 남기지 않는다. 결과에 `rejected` 로 세어 패널에 "실물 없는 그래픽 N장 제외"로 뜬다.

### 비용

사진 한 장이 API 호출 하나다. `ANTHROPIC_API_KEY` 가 없으면 분류만 막히고 검색·포트폴리오는 그대로 뜬다. 보드에서 한 번에 6/12/24장 중 고르고, 이미 라벨이 있는 사진은 경로로 걸러 건너뛰므로 같은 업체를 다시 눌러도 중복 과금은 없다. 모델은 `CLASSIFY_MODEL` 로 바꾼다(기본 `claude-opus-5`).

### 지금까지 확인한 것

`labels.jsonl` 의 아뜰리에 오화 `ig_*` 4건은 **모델이 아니라 사람이 눈으로 보고 단 라벨이다.** 파이프라인이 만들 결과물과 같은 모양이고, 보드에 반영되는 것까지 확인했다(드레스 52 → 56장, 실크 중심 롤업 15 → 17).

판정 안 되는 축은 비웠다. 앉은 자세라 밑단이 안 보이는 두 장은 라인 미부여, 흑백 사진은 색상 미부여 — 색상 축이 `화이트·아이보리/블랙/컬러` 셋뿐이라 흑백에서 찍으면 거짓말이 된다. 같은 규칙을 프롬프트에 적어뒀지만 **모델이 그대로 따르는지는 아직 검증하지 못했다.** 키를 넣고 같은 4장을 돌려 대조하는 게 가장 싼 검증이다.

## 플래너 인터뷰에서 업체찾기에 걸리는 것

베리굿웨딩 오사라 부장, S웨딩 윤다희 실장 두 분 피드백 중 **업체찾기에 해당하는 것만** 추렸다.

### 1. 드레스 분류 과세분화 — 라벨 데이터는 살린다

> 과도한 세분화(엠파이어, H라인, 프린세스)는 피하되, 실제 중요한 건 "실크 중심인가, 비즈 중심인가, 강한 비즈인가 / 맑은 비즈인가"

처음엔 148장 라벨을 다시 따야 하나 싶었는데, 확인해보니 그럴 필요가 없다. `taxonomy.json` v2의 **장식** 축에 `굵은비즈`, `잔잔비즈·글리터`가 이미 있다. 인터뷰가 말한 "강한 비즈 / 맑은 비즈"가 그대로 대응된다. 실크도 소재 축에 `새틴실크`, `미카도실크`로 있다.

**바꿀 건 라벨이 아니라 그 위의 집계 층이다.**

- `라인` 5종은 필터 전면에서 빼고 내부 메타로만 유지
- 업체 단위로 "실크형 / 비즈형(강·맑)" 롤업을 만들어 그걸 필터에 노출

### 2. 업체 카드의 단정 표기

[VendorsPage.tsx:162](../src/features/vendors/VendorsPage.tsx#L162)에서 `집중형`/`균형형`을 카드에 박아 보여준다. 그런데 인터뷰가 이걸 정확히 경고했다.

> "이 업체 = 과즙 메이크업"처럼 너무 강하게 분류하면 고객이 절대적 특성으로 인식할 수 있다. 실제로는 담당자의 영향이 매우 크다.

특히 메이크업은 업체 단위 라벨링 자체가 맞지 않을 수 있다. `labels.jsonl`에 담당자 축이 없어서 데이터 구조까지 이어지는 문제다.

### 3. 레퍼런스가 자주 바뀐다

> 업체 화보를 시스템 내에서 검색하고 고객별로 저장하는 기능은 유용하지만, 업체 화보가 자주 변경되므로 업데이트 관리가 필요하다

방금 만든 인스타 동기화가 이걸 푼다. 다만 아직 주기 갱신(크론)은 없다. 지금은 화면 진입 시 조회 + 10분 캐시뿐이다.

### 4. AI 추천의 방향이 다르다

> 경력 플래너는 이미 업체를 알고 있어 AI 추천이 필요 없을 수 있지만, 고객의 상담 전 레퍼런스 이미지 사전 확인은 매우 실용적이다

AI가 플래너에게 업체를 추천하는 그림이 아니라, **고객이 상담 전에 취향 이미지를 골라두는** 그림이다. 라벨링의 목적지가 바뀐다. 취향 보드가 실제 진입점이 된다.

### 5. 검색되는 업체 정보

두 분 다 원한 것이다. 촬영 추가비, 꽃 종류, 휴무일 같은 걸 전화 대신 검색으로 확인하고 싶어 한다. 커뮤니티냐 정보 DB냐로 의견이 갈렸지만, 실제로 원하는 건 둘 다 "검색되는 사실 정보"라 하나로 수렴시킬 수 있다.

## 내일 할 일 후보

우선순위순.

1. ~~**업체 검색·필터를 실제로 동작하게**~~ — 사진 단위로는 끝났다(레퍼런스 보드). 다만 **업체 목록 화면은 아직 목업**이다. 같은 검색 API 위에 업체 단위 집계를 얹으면 된다
2. ~~**집계 축 재설계**~~ — 롤업(`실크 중심 / 강한 비즈 / 맑은 비즈`)을 `facets.ts` 에 넣었다. 남은 건 이걸 업체 카드에도 쓰는 일
3. **담은 시안을 커플에 붙이기** — 지금은 화면 상태라 새로고침하면 날아간다. 인터뷰의 "고객별로 저장"이 여기다
4. **카드 표기 완화** — `집중형`/`균형형` 단정 표기를 손본다
5. ~~**이미지 자동 분류**~~ — 파이프라인은 끝났다. 남은 건 `ANTHROPIC_API_KEY` 를 넣고 모델 라벨을 사람 라벨과 대조하는 일
6. **일반 게시물 사전 필터** — 지금은 브랜드 그래픽도 일단 원본을 받아 분류에 태운 뒤 `usable` 로 버린다. 버릴 사진에 full-size 호출을 한 번씩 쓰는 셈이라, **썸네일이나 축소본으로 먼저 싸게 걸러내는 단계**를 앞에 두는 게 낫다. 6장 중 2장이 해당했으니 체감이 작지 않다

## 범위 밖 (다른 사람 몫)

인터뷰에서 나왔지만 내 담당이 아니다. 참고만 하고 건드리지 않는다.

- **견적 분리** — 웨딩홀과 스드메를 갈라야 한다. 보증 인원에 따라 수백만 원이 달라지고 거래 구조도 다르다
- **상태 기반 리마인드** — "D-7인데 상품 미결정" 같은 상태 추적. 날짜 알림보다 중요하다는 평
- **발주 승인 추적** — "알림을 믿지 않고 거의 매일 직접 확인"한다는 문제. 기능 자체는 "이건 너무 좋은데" 호평
- **플래너 커뮤니티** — 두 분 의견이 갈렸다
- **이동시간 계산** — "빼셔도 될 것 같다"는 평가. [TravelLegBlock.tsx](../src/features/calendar/TravelLegBlock.tsx) 삭제 후보지만 캘린더 담당자와 상의할 일
- **멀티테넌시** — 컨설팅사마다 제휴 업체가 다르다. DB 스키마를 짜기 전에 팀에서 정해야 한다
